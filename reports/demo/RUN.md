# Reference run — demo sample

Everything in this directory is **pipeline output**, written by `authbench demo`
(equivalently `make demo`) and committed **on purpose**, unlike every other
artifact in `reports/`. It is here so that the benchmark's results can be read
without running anything, and so that CI can prove, on every push, that they
regenerate byte for byte.

## What this is — and what it is not

**Not a LANL result. Not a finding about any model.** The input is
`data/demo/auth_demo.txt`, a deterministic synthetic sample generated by
`scripts/generate_demo_data.py`. Its purpose is to exercise the whole protocol
end to end in under a minute, not to measure anything about the world.

| | |
|---|---|
| Auth events | 37,844 |
| Period | 14 days |
| Red-team events | 27, in **10 campaigns** |
| Campaigns per partition | train 3 · val 3 · **test 4** |
| Positive rate | 7.1 × 10⁻⁴ — about **1,000× LANL's**. A smoke test, not a scale model. |
| Split | temporal, train days 0–7 · val 8–10 · test 11–13 |

The campaign counts are a design parameter, not an accident, and the test split's
four are load-bearing: campaigns are the independent unit of the
campaign-stratified bootstrap, so they *are* its sample size. An earlier sample
put one campaign in the test split, and the comparison table came back 21 pairs
out of 21 "significant" — off a single attack, at the bootstrap's own resolution
floor. See `_CAMPAIGNS_PER_PARTITION` in the generator and
`stats_tests.MIN_CAMPAIGNS_FOR_SIGNIFICANCE`.

## The result on this sample is partly circular

Stated here as well as in the README, because this directory is where someone
lands who wants to quote a number.

The generator emits campaigns as chains (user authenticates A→B, then B→C) and
M1's rule R7 tests for "previous destination equals current source within 30
minutes" — the same predicate. Measured on the test split, R7 scores 113× higher
on malicious events than benign ones, and M1's validation-fitted weights put
0.521 of their mass on it. R1 (new user→host pair) contributes genuinely at 2.5×;
R4 (off-hours) does not discriminate at all; R2, R3 and R5 never fire.

So "M1 catches every campaign at 10 alerts/day" is, here, mostly one rule that
was handed the generator's own definition of an attack. The
alert-budget-versus-ROC-AUC gap in the same table does **not** depend on this —
it is a property of the operating point, not of the sample — but the model
*ranking* does. Do not quote the ranking as a finding.

## One row is a tie, not a measurement

M0b always-fail scores every event 0 or 1, so at budget 500 some 7,899
equally-scored events compete for 1,350 places and *something* has to order
them. `tables/demo_results.json` reports that directly: the
`campaign_recall_tie_bracket` on M0b's row spans `[0, 1]` at budgets 100 and
500, and `tie_exposure` gives the slots and the contenders behind it. Every
other model's bracket has zero width — their scores leave the ordering nothing
to decide — which is why the headline figure shades one band and not seven.

This changed a published number. Before the ordering was made explicit, ties
broke on the frame's row order, which after `features.temporal.compute_f4` is
`(src_user, time)` — so M0b's alerts were the failures of the alphabetically
earliest users, and it caught nothing at any budget. Under arrival order it
catches 3 of 4 campaigns at budget 500. The honest reading is neither figure on
its own: at this budget M0b's recall is somewhere in `[0, 1]` and the run cannot
narrow it.

## Files

| File | What it holds |
|---|---|
| `tables/demo_results.json` | every metric, per model, operational and literature-comparable kept separate — the operational block also carries `campaign_recall_tie_bracket`, `tie_exposure` and `budget_for_first_detection` |
| `tables/pairwise_comparisons.json` | all 21 pairwise AUC-PR tests: `p_value_raw`, `p_value_holm_adjusted`, and `at_resolution_floor` — set on all 8 significant pairs here, meaning their p-value is the bound `2/(R+1)` rather than a value the bootstrap resolved |
| `tables/campaign_summary.csv` | one row per red-team campaign: user, event count, duration |
| `figures/campaign_recall_vs_budget.png` | the headline figure |
| `data_quality.json` | null rates, cardinalities, counted drops |

## Reproducing it

```bash
make demo        # ~40 s; rewrites this directory in place
git diff --stat reports/demo
```

The diff must come back empty. Every seed is pinned (`seed=42` for the models,
the M1 weight search and the bootstrap alike), and CI runs exactly this check —
`tests/unit/test_campaign_blocks.py` covers the specific failure that used to
break it, where Polars' unordered `group_by` reshuffled the bootstrap's blocks
between runs and quietly drifted every confidence interval while leaving the
point estimates untouched.
